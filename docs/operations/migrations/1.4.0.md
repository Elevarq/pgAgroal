# Migration to 1.4.0 (hardened shipped defaults)

This release does **not** change the bundled upstream pgagroal version — it
remains **2.1.0**. It hardens the **shipped configuration defaults** of the
Elevarq pgAgroal packaging (Elevarq packaging v1.4.0). Several defaults now
restrict access where the previous (1.3.x) defaults were permissive, so
deployments that relied on the old open behaviour must opt back in
explicitly.

This is a configuration change, not a data-format change: there is **no
re-keying and no on-disk migration**. `Class: breaking-config` applies
because the shipped defaults change observable behaviour (who may connect,
and how) in a way that is not transparent to an existing deployment.

## What changed, and how to restore the old behaviour

| Default | 1.3.x | 1.4.0 | Restore 1.3.x behaviour |
|---|---|---|---|
| HBA source addresses | `host all all all all` (any source) | RFC1918 CIDR allowlist, `scram-sha-256` | `PGAGROAL_HBA_SOURCE=all` (Helm: `pgagroal.hbaSource=all`) |
| `allow_unknown_users` | `true` (passthrough) | `false` | `PGAGROAL_ALLOW_UNKNOWN_USERS=true` (Helm: `pgagroal.allowUnknownUsers=true`) |
| Helm NetworkPolicy | none | enabled; denies ingress from other namespaces, allows same-namespace | `networkPolicy.enabled=false` |
| compose published ports | all interfaces | `127.0.0.1` only | change the bind to `0.0.0.0:<port>:<port>` |
| pgexporter metrics bind | `*` | `0.0.0.0` (IPv4); exposure bounded at the publish / NetworkPolicy layer | n/a (functionally equivalent) |

Egress containment is **opt-in** (`networkPolicy.restrictEgress`, default
off), so it does not change behaviour unless you enable it.

## Who is affected

- **Clients outside RFC1918, or in another namespace.** If your application
  pods connect from a non-RFC1918 pod network (for example an EKS
  `100.64.0.0/10` secondary CIDR) or from a different namespace, they are
  denied by default. Set `pgagroal.hbaSource` to your pod CIDR and/or admit
  the namespace with `networkPolicy.ingressNamespaceSelectors`.
- **Deployments relying on unknown-user passthrough.** With
  `allow_unknown_users=false`, every user must be registered with pgagroal
  (`PG_USERNAME` / `PG_PASSWORD`, or a Secret). If you relied on transparent
  passthrough, set `allowUnknownUsers=true` or register the users.
- **Anyone who later enables egress containment** must set
  `networkPolicy.egress.kubeDNS` to the cluster resolver (EKS CoreDNS is
  `10.100.0.10/32`, not the `10.96.0.10/32` kubeadm default) or DNS — and
  therefore backend resolution — will break.

Deployments that already use scoped networks, registered users, and a
NetworkPolicy are unaffected: the new defaults match what you already run.

## Migration procedure

This is a configuration change; no data migration is required.

1. Review the table above against your current values / environment.
2. **Helm.** Update your values for any old behaviour you depend on
   (`pgagroal.hbaSource`, `pgagroal.allowUnknownUsers`, `networkPolicy.*`),
   then upgrade:

   ```bash
   helm upgrade pgagroal helm/pgagroal/ -n <namespace> \
     --set image.tag=1.4.0 -f your-values.yaml
   ```

   **Docker / Compose.** Set the image to `elevarq/pgagroal:1.4.0`, provide
   `PG_USERNAME` / `PG_PASSWORD` (or `PGAGROAL_ALLOW_UNKNOWN_USERS=true`), and
   set `PGAGROAL_HBA_SOURCE` if your clients are outside RFC1918.
3. Restart / roll the deployment — configuration is read at start, not on
   `pgagroal-cli reload`.

## Verification

```bash
# Confirm the bundled pooler version
kubectl exec deploy/pgagroal -n <namespace> -- pgagroal-cli --version
# Expect: pgagroal-cli 2.1.0 ...

# A registered/allowed client can connect through the pool
psql "host=<pgagroal-host> port=6432 user=<user> dbname=<db>"
```

If a client is refused with an HBA error, its source address is outside the
allowlist — add its CIDR to `pgagroal.hbaSource`. If a Kubernetes client
cannot reach the pooler at all, it is likely in another namespace — admit it
with `networkPolicy.ingressNamespaceSelectors` (or adjust
`networkPolicy.allowSameNamespace` / selectors).

## Rollback

Roll the image back to `elevarq/pgagroal:1.3.0` and, if you added it, remove
the NetworkPolicy (`networkPolicy.enabled=false`). No data changes are
involved, so rollback is a redeploy.

## Why this is `Class: breaking-config`

Per `specifications/project-release/spec.md`, this release is
`breaking-config` because the shipped defaults change who may connect and
how. That is operator-visible and not safe to assume transparent on a
rolling upgrade — even though no on-disk data format changes in this release.
