# Migration to 1.1.0-rc1 (pgagroal 2.1.0)

This release upgrades the bundled upstream pgagroal from **2.0.2** to
**2.1.0**. Upstream 2.1.0 introduces two breaking changes that affect
operators of this container:

1. **Vault encryption format**, and on-disk user / admin / superuser
   files, are re-keyed with AES-256-GCM. Existing vaults from 2.0.x
   cannot be read.
2. **Management wire protocol** is GCM-only — legacy CBC and CTR are
   removed. A 2.0.x `pgagroal-cli` / `pgagroal-vault` cannot talk to
   a 2.1.0 server, and a 2.1.0 client cannot talk to a 2.0.x server.

Both changes are mandatory and there is no opt-out flag. Plan the
upgrade as a coordinated cutover, not a rolling change.

Upstream reference: https://github.com/pgagroal/pgagroal/blob/2.1.0/doc/MIGRATION.md

## Who is affected

| Surface | Affected? | Why |
|---|---|---|
| User / admin / superuser auth files | Yes | re-encrypted with new format |
| Master key (`master.key`) | Yes | rotated; old key cannot decrypt new files |
| Frontend users (`pgagroal_frontend_users.conf`) | Yes | re-encrypted |
| `pgagroal-cli` clients | Yes | must run 2.1.0 to manage a 2.1.0 server |
| `pgagroal-vault` clients | Yes | same as cli |
| TLS certificates and CA files | No | unchanged by this release |
| Connection pooling, pipelines, HBA rules | No | unchanged by this release |
| PostgreSQL backend | No | the upgrade does not affect the upstream Postgres protocol |

If you do not use the vault, frontend users, or remote management,
the upgrade is still a config rotation — the master key and any
encrypted user files must still be regenerated, because the embedded
encryption format is upgraded for all encrypted artifacts.

## Pre-flight

Before starting:

- [ ] Take a current snapshot of `/etc/pgagroal/` (or wherever your
      mount lives). The new files cannot be reverted from the old
      ones, so a snapshot is your only roll-back path.
- [ ] Confirm you have the source-of-truth list of users that need to
      be re-added (passwords cannot be recovered from the existing
      encrypted files using the new key).
- [ ] Confirm every operator that runs `pgagroal-cli` or
      `pgagroal-vault` against the deployment is ready to upgrade
      their tooling at the same time.
- [ ] Schedule a maintenance window. Connections through pgagroal
      will be interrupted while the pod / container restarts.

## Migration procedure

The procedure below assumes the container's Helm chart deployment.
For Docker Compose, the same steps apply against the mounted
`/etc/pgagroal` volume.

### 1. Stop pgagroal

```bash
kubectl scale deployment pgagroal --replicas=0 -n <namespace>
```

For Docker Compose:

```bash
docker compose stop pgagroal
```

### 2. Remove the encrypted user files and master key

These files are inside the configuration directory mounted at
`/etc/pgagroal/` in the container. With the running container
stopped, edit the underlying volume directly:

```
pgagroal_users.conf
pgagroal_frontend_users.conf
pgagroal_admins.conf
pgagroal_superuser.conf
master.key
```

Plus the vault users file if your deployment uses
`pgagroal-vault`.

Each file that exists in your deployment must be removed. Files that
were never created can be skipped.

### 3. Upgrade the image

Update your Helm `values.yaml`:

```yaml
image:
  repository: elevarq/pgagroal
  tag: "1.1.0-rc1"
```

```bash
helm upgrade pgagroal helm/pgagroal/ -n <namespace>
```

For Docker Compose, change the `image:` line to
`elevarq/pgagroal:1.1.0-rc1` and `docker compose pull`.

### 4. Regenerate the master key inside the new container

Once the new container is up:

```bash
kubectl exec -it deploy/pgagroal -n <namespace> -- \
  pgagroal-admin master-key
```

You will be prompted for a new passphrase. Choose one that meets
your password policy and store it in your secrets manager — there is
no recovery if it is lost.

### 5. Re-add users

For each user that previously existed:

```bash
kubectl exec -it deploy/pgagroal -n <namespace> -- \
  pgagroal-admin user add -f /etc/pgagroal/pgagroal_users.conf
```

Repeat for `pgagroal_frontend_users.conf`,
`pgagroal_admins.conf`, and `pgagroal_superuser.conf` as required by
your deployment.

### 6. Restart pgagroal

The configuration file changes are picked up only on (re)start, not
on `pgagroal-cli reload`. Force a fresh start:

```bash
kubectl rollout restart deployment pgagroal -n <namespace>
```

### 7. Upgrade every `pgagroal-cli` / `pgagroal-vault` client

This is the second breaking change. A 2.0.x cli cannot talk to a
2.1.0 server. Every operator workstation, CI pipeline, and ad-hoc
script that runs `pgagroal-cli` or `pgagroal-vault` against this
deployment must be upgraded to 2.1.0 simultaneously.

For workstations using `elevarq/pgagroal:<X.Y.Z>` as a CLI shim,
update the pinned tag to `1.1.0-rc1`.

## Verification

After the migration:

```bash
# Confirm version
kubectl exec deploy/pgagroal -n <namespace> -- pgagroal-cli --version
# Expect: pgagroal-cli 2.1.0 ...

# Confirm health
kubectl exec deploy/pgagroal -n <namespace> -- \
  pgagroal-cli -c /etc/pgagroal/pgagroal.conf ping
# Expect: success, including PostgreSQL backend reachability (new in 2.1.0)

# Confirm a user can connect through the pool
psql "host=<pgagroal-host> port=6432 user=<re-added-user> dbname=<db>"
```

If `pgagroal-cli ping` fails with a protocol error, the cli binary is
still at 2.0.x — see step 7.

## Rollback

There is no in-place rollback path. If the migration fails:

1. Restore the snapshot taken in pre-flight to recover the old
   encrypted files and the old `master.key`.
2. Roll the image back to `elevarq/pgagroal:1.0.1`.
3. Restart pgagroal and clients with the 2.0.x cli.

Plan and rehearse the rollback before applying the migration in
production.

## Why this is `Class: breaking-config`

Per `specifications/project-release/spec.md`, this release is
classified `breaking-config` because:

- It requires operator-visible action (re-keying, file deletion, user
  re-add) that is not transparent to the running deployment.
- It is not safe to apply as a rolling upgrade — server and clients
  must move together.
- Existing on-disk encrypted artifacts cannot be migrated forward
  automatically.

The release is published only as `elevarq/pgagroal:1.1.0-rc1` (RC).
The `1.1` and `latest` aliases continue to point at `1.0.1` until
the RC has been validated and `v1.1.0` is cut.
